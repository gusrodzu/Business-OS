## Acciones operativas pendientes que requieren acceso a infraestructura

1. **GitHub Settings / Code security:** habilitar secret scanning, push protection (según plan) y Dependabot alerts; revisar los avisos y activar CodeQL si está disponible.
2. **GitHub Branch protection:** requerir revisión humana, las suites Frontend QA, Dependency Security Triage, Prisma y MotorNorte, y prohibir push directo a `main`. Verificar que ningún check obligatorio quede vinculado a nombres de jobs que cambien.
3. **Secretos en producción:** verificar que `JWT_SECRET`, `MFA_ENCRYPTION_KEY`, `INTEGRATION_ENCRYPTION_KEY`, credenciales PostgreSQL y S3 sean únicas por ambiente, aleatorias y gestionadas desde el proveedor. Planear rotación controlada, ya que rotar JWT revoca sesiones y rotar claves de cifrado exige migración/recifrado previo.
4. **Render/API:** `CLIENT_URL` exacto (sin wildcard), HTTPS, `COOKIE_SECURE=true`, `ALLOW_LEGACY_BEARER_AUTH=false`, almacenamiento privado S3 y proxy confiable; no exponer PostgreSQL a Internet.
5. **Base de datos:** confirmar acceso con mínimo privilegio, copias cifradas, calendario de respaldo y restauración de prueba aislada; preservar el respaldo anterior a cualquier migración.
6. **MFA y contraseñas:** verificar MFA de todos los administradores, deshabilitar cuentas de muestra si llegaron a existir en un ambiente real y forzar cambio de contraseñas públicas o reutilizadas.
7. **Prueba de seguridad externa:** ejecutar comprobaciones de autorización, IDOR, CSRF, subida de archivos, fuga de metadatos, sesión y cabeceras en un entorno de staging. No realizar pruebas invasivas contra producción sin un plan y autorización.

## Riesgos no cerrados por este PR

- El limitador MFA/IP vive en memoria de cada instancia. Con varios servidores no es distribuido; migrar a Redis o equivalente y añadir límites por cuenta/challenge.
- Dependabot y `npm audit` no cubren todos los riesgos (secretos filtrados, configuración cloud, código propio, dependencias que no estén en npm).
- No se ha verificado el funcionamiento end-to-end del frontend publicado con su backend real ni se han consultado los logs de Vercel para los previews fallidos.
- Los scripts de semilla con credenciales de demostración nunca se deben utilizar para inicializar clientes reales: hace falta un flujo de bootstrap de administrador con contraseña/clave aleatoria e invitación segura.
- El dashboard y rutas locales offline siguen siendo una simulación; no constituyen una prueba de autenticación real de producción.
